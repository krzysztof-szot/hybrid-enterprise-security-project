## Scenario 1 — Azure RBAC detection and response

### Prevent and establish a baseline

Sara's Current role assignments panel showed **0** assignments at the target resource group. The initial portal attempt failed with HTTP 403 / AuthorizationFailed for **Microsoft.Resources/subscriptions/read**. This was a subscription-read failure encountered while opening the group, not a direct resourceGroups/read result. Eligible assignments were not displayed.

An administrator then granted **Reader** at **rg-bfl-sentinel-lab**, shown as **This resource / Active Permanent**. The role was not PIM-eligible or automatically expiring; the exercise later removed it explicitly. The owner opened the law-bfl-sentinel Overview page in Sara's test session and supplied the successful view. No write-denial test was performed in Day 15.

### Detect

The rule was enabled before the test grant and the Day 14 rule stayed Disabled.

| Setting | Saved value |
|---|---|
| Type / severity | Scheduled / Informational |
| Frequency / lookback | Every 5 minutes / last 15 minutes |
| Alert threshold | Greater than 0 results |
| Event grouping | All results into one alert |
| Suppression | Not configured |
| Incident creation | Enabled |
| Alert grouping | Enabled; all alerts generated by this rule, one-hour period |
| Final state | Disabled |

Description: Detect successful Azure role assignment changes in rg-bfl-sentinel-lab. Validate the recipient, role and business justification during investigation.

The scheduled query used during the session is reproduced below. Its time window is supplied by the rule schedule. Screenshot 03 shows only a portion of the query; screenshot 06 shows the interactive version, and screenshot 07 establishes a matching runtime alert. No complete rule JSON export was collected.

```kusto
AzureActivity
| where OperationNameValue =~ "Microsoft.Authorization/roleAssignments/write"
| where ActivityStatusValue in~ ("Success", "Succeeded")
| extend TargetResource = coalesce(
    _ResourceId,
    ResourceId,
    tostring(Authorization_d.scope))
| where TargetResource contains "/resourcegroups/rg-bfl-sentinel-lab/"
    or TargetResource endswith "/resourcegroups/rg-bfl-sentinel-lab"
| project TimeGenerated, OperationNameValue,
          ActivityStatusValue, TargetResource,
          Caller, CorrelationId
```

For the interactive verification, `| where TimeGenerated > ago(1h)` was added immediately after AzureActivity, and `| order by TimeGenerated desc` was appended.

This matches successful role-assignment writes within the named resource group. It does not establish a dangerous role, malicious intent or a particular recipient by itself. The path filter does not uniquely constrain the subscription if reused in a workspace receiving multiple subscriptions with identically named groups.

### Investigate

The successful operation occurred at **14:30:01.7997622 UTC**. Its correlation ID, **fd08d57f-09e3-4f3a-bee9-8c2cfba55f65**, matched the related event in the Sentinel alert.

Inspection of Properties_d did not expose requestbody or the recipient/role. Caller was the administrative actor, not Sara. The role-assignment resource identifier from the log was therefore used in a read-only Azure CLI query:

```bash
az role assignment list --resource-group rg-bfl-sentinel-lab --query "[?name=='5522728c-1a98-429b-b2b6-5b72cdc38b60'].{Assignment:name,Recipient:principalName,Role:roleDefinitionName,Scope:scope}" --output json
```

The returned assignment ID matched the event target; its recipient was **bfl.sara.security**, role **Reader**, and scope **rg-bfl-sentinel-lab**. This joined the detection to the actual authorization change rather than assuming that the log actor was the beneficiary.

The observed event-to-alert interval was approximately 13 minutes 7 seconds, not a detection SLA. Two alerts shared the activity time; overlapping 5/15-minute windows are a plausible explanation, but rule-run records were not exported to prove the cause. No entities were mapped.

### Respond and verify

The administrator removed Sara's Reader assignment. Check access returned **0 current role assignments**. The subsequent test in Sara's fresh session displayed **You don't have access**, portal error code **401**, and specifically denied **Microsoft.Resources/subscriptions/resourceGroups/read**.

The incident was classified using the Defender form's **Informational, expected activity** category; guidance selected Security test. The saved incident header shows **Benign Positive / Resolved**, with both alerts resolved. The exact determination and investigation-comment text are not visible and are not treated as independently verified.

The Day 15 rule was disabled after completion. The final Analytics view shows both demonstration rules Disabled and 0 active rules. Role removal was verified through IAM and denied access; no roleAssignments/delete log or separate revocation alert was collected.

## Scenario 2 — Endpoint compliance and Conditional Access

### Baseline

The owner confirmed that Anna could sign in to BFL-WKS02 and that its check-in was current. Intune showed Corporate, Compliant and Anna as primary user. The policy's Firewall, Antivirus and TPM checks were all Compliant. Outlook Web opened successfully.

The owner confirmed that CA-BFL-Pilot-Require-Compliant-Device included Anna and Office 365, required a compliant device and was **On**. This was not a report-only exercise. Included group BFL-Intune-Pilot-Devices and a zero-day noncompliance action were also confirmed.

### Controlled failure

Minimum OS version was initially **Not configured**, shown in the supplied editor text. It was temporarily set to **10.0.26301.0**, higher than the supplied installed build **26300.9457**. This threshold was chosen solely to fail the test device; it is not a recommended production version baseline.

The saved policy retained Firewall, TPM and Antivirus as Required, with **Mark device noncompliant: Immediately**. Synchronization was requested in Intune and on the endpoint. The report then showed **Minimum OS version: Not compliant**, while the three protective controls remained Compliant.

Outlook sign-in displayed the device-compliance block page. The matching test sequence was investigated in Entra's interactive sign-in logs:

- **15:57:05 UTC:** One Outlook Web, status Failure.
- **CA-BFL-Pilot-Require-Compliant-Device:** Failure.
- **Grant control:** RequireCompliantDevice.

The application screenshot alone was not used to identify the blocking policy; the sign-in event supplied that evidence. No numeric Entra error code or full Device info export was captured.

### Restore and verify

The rollback instruction was to clear Minimum OS version back to **Not configured**, save and synchronize, keeping Conditional Access enabled. The subsequent evidence shows:

- BFL-WKS02 **Compliant**, with a check-in at **18:21 local**.
- Outlook Web open again in the test session.
- **16:23:48 UTC:** One Outlook Web, status **Success**.
- The same CA policy and RequireCompliantDevice control evaluated as **Success**.

The recovered state and applied CA Success are directly evidenced. The final policy editor was not captured, so the exact restored Minimum OS version field is not independently exported. Recovery was achieved in the guided rollback workflow, without recording a Windows upgrade or disabling the CA policy.

## Troubleshooting and lessons

- **Actor versus recipient:** AzureActivity Caller identifies who performed the operation. The exact assignment resource must be inspected to establish who received the role.
- **Incomplete event payload:** Properties_d contained no requestbody for the inspected event. Querying the live assignment by its ID provided the missing recipient, role and scope.
- **Alert versus incident status:** Resolved alerts did not initially establish incident classification. The final incident screenshot verified ID 5, Resolved and Benign Positive.
- **Classification terminology:** The Defender form offered Informational, expected activity; the final incident header displayed Benign Positive. An accurate authorized test was not labelled a malicious attack.
- **Configuration versus enforcement:** An IAM assignment and an Intune status were each followed by functional access checks. Entra's CA tab identified the specific policy responsible for denial and success.
- **Controlled compliance failure:** A temporary OS requirement isolated the test condition while Firewall, Antivirus and TPM stayed compliant.
- **Timestamps:** AzureActivity and Entra event-list values are UTC; the Defender and Intune overview captures use local display time, UTC+2 in Poland on this date.
